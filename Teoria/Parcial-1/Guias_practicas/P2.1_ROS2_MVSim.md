## 1. Visión general

En esta práctica intervienen tres capas diferentes:

1. **MVSim** crea la realidad simulada: mundo, robot, sensores y física.
2. **ROS 2** comunica los distintos programas mediante nodos, topics y mensajes.
3. **RViz2** visualiza la información que circula por ROS 2.

Una forma útil de recordarlo es:

```text
Archivo world.xml -> MVSim -> topics ROS 2 -> RViz2 y nodos de control
```

MVSim sabe dónde se encuentra realmente el robot. Los demás nodos solo conocen aquello que reciben a través de ROS 2, de forma parecida a lo que ocurriría con un robot físico.

## 2. ROS 2 como sistema distribuido

ROS 2 no es un único programa. Es un entorno en el que varios componentes en ejecución, llamados **nodos**, colaboran entre sí. Normalmente se ejecutan en procesos independientes, aunque un proceso también puede alojar varios nodos.

Cada nodo tiene una responsabilidad concreta. Por ejemplo:

- `mvsim` simula el mundo, publica sensores y recibe órdenes de movimiento.
- `rviz2` recibe datos y los representa gráficamente.
- Un futuro nodo `keyboard_control` leerá el teclado y publicará velocidades.

Los nodos no necesitan estar escritos en el mismo lenguaje ni ejecutarse dentro del mismo proceso. Su contrato de comunicación viene determinado por:

- El nombre del **topic**.
- El tipo del **mensaje**.
- Las políticas de **QoS**.

Esta separación reduce el acoplamiento. Un sensor puede publicar datos sin saber qué nodos los utilizarán, y un consumidor puede incorporarse más tarde sin modificar el sensor.

## 3. MVSim y los archivos de mundo

MVSim es un simulador dinámico de vehículos y robots terrestres. Un escenario se describe mediante un archivo XML cuya extensión habitual es `.world.xml`.

El archivo de mundo contiene, entre otros elementos:

- Parámetros generales de simulación.
- Configuración de la interfaz gráfica.
- Geometría del entorno.
- Vehículos presentes.
- Posiciones iniciales.
- Sensores instalados.
- Referencias a definiciones reutilizables.

El mundo usado en la práctica es:

```text
/opt/ros/jazzy/share/mvsim/mvsim_tutorial/demo_indoor_outdoor.world.xml
```

Para localizar de forma portable los recursos instalados de un paquete se utiliza:

```bash
ros2 pkg prefix --share mvsim
```

No conviene asumir siempre `/opt/ros/jazzy/share/mvsim`, porque un paquete también podría estar instalado en un workspace del usuario.

### Variables y expresiones

Los mundos pueden definir variables:

```xml
<variable name="INDOOR_ROOM_SIZE" value="10.0" />
<variable name="CORRIDOR_STRAIGHT_LENGTH" value="20.0" />
```

Después pueden emplearlas en expresiones:

```xml
<init_pose>$f{-CORRIDOR_STRAIGHT_LENGTH-0.5*INDOOR_ROOM_SIZE-5} 0 0</init_pose>
```

Con los valores anteriores, la coordenada inicial es:

$$
x=-20-0.5\cdot 10-5=-30
$$

La pose se expresa como `x y yaw`, donde `yaw` es la orientación alrededor del eje vertical.

## 4. Vehículos, sensores e includes

MVSim permite reutilizar definiciones mediante `<include>`. El mundo no necesita repetir toda la geometría y dinámica del Jackal; incluye su clase:

```xml
<include file="../definitions/jackal.vehicle.xml"
  default_sensors="false"
  joyMaxLinSpeed="3.0"
/>
```

El vehículo concreto se instancia después:

```xml
<vehicle name="robot" class="jackal">
  ...
</vehicle>
```

Hay que distinguir:

- **Clase**: plantilla reutilizable, en este caso `jackal`.
- **Instancia**: vehículo concreto del mundo, llamado `robot`.

### Includes parametrizados

Los atributos de un `<include>` actúan como argumentos. Una definición incluida puede usar una expresión como:

```text
${sensor_yaw|0.0}
```

Esto significa: usar el valor recibido en `sensor_yaw` o, si no se proporciona, usar `0.0`.

También puede haber bloques condicionales:

```xml
<if condition="${default_sensors|true}">
  ...
</if>
```

Por tanto, `default_sensors="false"` desactiva todo el bloque de sensores predeterminados.

### Sensores del robot

La clase original del Jackal puede incorporar:

- LiDAR 2D `scanner1`.
- LiDAR 3D `lidar1`.
- Cámara RGB `cam1`.

El archivo de mundo añade además:

- Receptor GNSS `gps1`.
- Unidad de medición inercial `imu`.

En la configuración ligera se desactivan los sensores predeterminados y se vuelve a añadir únicamente el LiDAR 2D desde el archivo de mundo.

## 5. Optimización para una máquina virtual

Una cámara y un LiDAR 3D requieren renderizado y procesamiento considerable. Dentro de una máquina virtual, la aceleración OpenGL suele ser limitada, por lo que la simulación puede ejecutarse lentamente o fallar.

La solución de la práctica sigue dos pasos:

1. Desactivar los sensores predeterminados de la clase:

```xml
<include file="../definitions/jackal.vehicle.xml"
  default_sensors="false"
  joyMaxLinSpeed="3.0"
/>
```

2. Montar manualmente solo el LiDAR 2D necesario:

```xml
<include file="../definitions/lidar2d.sensor.xml"
  sensor_x="0.15" sensor_y="0.0" sensor_z="0.25" sensor_yaw="0"
  sensor_period_sec="0.10"
  sensor_name="scanner1"
  raytrace_3d="true"
  fov_degrees="270"
/>
```

### Significado de los atributos del sensor en el XML

Estos valores configuran el sensor en el archivo de mundo de MVSim. Aunque se puedan llamar «parámetros» en sentido general, **no son parámetros ROS 2 de un nodo** que se consulten con `ros2 param get`.

- `sensor_x="0.15"`: sensor situado 15 cm por delante del origen del robot.
- `sensor_y="0.0"`: centrado lateralmente.
- `sensor_z="0.25"`: situado a 25 cm de altura.
- `sensor_yaw="0"`: orientado hacia delante.
- `sensor_period_sec="0.10"`: una medida cada 0,1 s.
- `sensor_name="scanner1"`: nombre usado para el topic.
- `raytrace_3d="true"`: los rayos colisionan con la geometría 3D real.
- `fov_degrees="270"`: campo de visión de 270 grados.

La frecuencia teórica del sensor es:

$$
f=\frac{1}{T}=\frac{1}{0.10}=10\ \text{Hz}
$$

Una medición de aproximadamente `9.7 Hz` es razonable debido a la planificación del sistema, la carga de la máquina virtual y el coste de la simulación.

### Por qué no modificar la clase compartida

`jackal.vehicle.xml` puede ser utilizado por muchos mundos. Modificarlo alteraría todos ellos. Cambiar únicamente `demo_indoor_outdoor.world.xml` mantiene la personalización localizada y evita efectos secundarios.

## 6. Launch files y arranque de la simulación

Un **launch file** permite iniciar varios nodos y configurarlos mediante un solo comando:

```bash
ros2 launch mvsim demo_indoor_outdoor.launch.py
```

En esta práctica, el launch file específico prepara el mundo y reutiliza un launch file genérico que inicia:

- El nodo `mvsim_node`.
- RViz2, si `use_rviz` es verdadero.

### Consultar argumentos

Los argumentos disponibles se inspeccionan sin abrir el archivo:

```bash
ros2 launch mvsim demo_indoor_outdoor.launch.py --show-args
```

Algunos argumentos relevantes son:

- `headless`: ejecuta MVSim sin interfaz gráfica.
- `use_rviz`: decide si se abre RViz2.
- `world_file`: ruta del mundo que se cargará.
- `do_fake_localization`: publica una transformación ficticia `map -> odom`.
- `publish_tf_odom2baselink`: publica `odom -> base_link`.
- `force_publish_vehicle_namespace`: fuerza un namespace por vehículo.
- `disable_sim_time_clock`: utiliza tiempo real en lugar del reloj simulado.

Los argumentos se pasan con la sintaxis `nombre:=valor`:

```bash
ros2 launch mvsim demo_indoor_outdoor.launch.py headless:=true
```

En este caso no se abre la GUI de MVSim, pero RViz2 continúa activo porque `use_rviz` conserva su valor predeterminado `true`. `headless` y `use_rviz` son **argumentos del launch**: sirven para decidir cómo arrancar los programas. El launch pasa `world_file` al nodo `/mvsim` como **parámetro ROS 2**; un argumento y un parámetro pueden tener el mismo nombre, pero pertenecen a mecanismos distintos.

### Detener un launch

Se utiliza `Ctrl+C` en la terminal desde la que se inició. Esto envía una interrupción y permite que el sistema cierre los nodos lanzados.

## 7. MVSim GUI frente a RViz2

Aunque ambas ventanas muestran el mismo experimento, representan cosas diferentes.

### MVSim GUI

Es la realidad simulada o **ground truth**:

- Muestra la geometría completa del escenario.
- Conoce la pose exacta del robot.
- Representa la física y las colisiones.
- Puede mostrar modelos visuales no accesibles para el robot.

### RViz2

Es un visualizador de ROS 2:

- Solo dibuja datos recibidos mediante topics y transformaciones.
- No conoce directamente el archivo de mundo.
- Puede representar mapas, nubes de puntos, láseres, modelos y poses.
- Su aspecto esquemático no implica que la simulación esté incompleta.

Un mapa de ocupación suele usar:

- Blanco: espacio libre.
- Negro: obstáculo.
- Gris: espacio desconocido.

La separación entre ambas ventanas reproduce una idea fundamental: el robot no tiene acceso directo a la realidad completa, sino a observaciones producidas por sus sensores.

## 8. Nodos, topics, mensajes, servicios, parámetros y acciones

### Cómo encajan en esta práctica

| Concepto | Pregunta que responde | Ejemplo en la práctica 2.1 |
| --- | --- | --- |
| **Nodo** | ¿Quién hace el trabajo? | `/mvsim` simula el robot; `/rviz2` visualiza datos; el nodo de teleoperación controla el robot si lo creas. |
| **Topic** | ¿Por dónde circulan los datos o las órdenes sin esperar respuesta? | `/scanner1` lleva lecturas del láser y `/cmd_vel` lleva velocidades. |
| **Mensaje** | ¿Qué estructura tienen los datos que circulan? | `sensor_msgs/msg/LaserScan` en `/scanner1`; `geometry_msgs/msg/Twist` en `/cmd_vel`. |
| **Servicio** | ¿Cómo pido algo puntual y recibo una respuesta? | No se implementa un servicio propio en esta práctica. |
| **Parámetro ROS 2** | ¿Con qué valor se configura un nodo? | `world_file` indica al nodo `/mvsim` el archivo de mundo que debe cargar. |
| **Acción ROS 2** | ¿Cómo encargo una tarea larga con progreso y posibilidad de cancelarla? | No se utiliza una acción ROS 2 en esta práctica. |

El flujo principal es:

```text
Nodo de teleoperación (o ros2 topic pub) -> /cmd_vel -> /mvsim
/mvsim -> /scanner1 -> /rviz2
```

### Nodo: quién publica o recibe

Un **nodo** es un componente ROS 2 en ejecución; puede publicar, suscribirse, ofrecer servicios o ejecutar acciones. Habitualmente un ejecutable crea un nodo, pero un proceso puede contener más de uno. En el launch de esta práctica, `mvsim_node` es el **ejecutable** y `/mvsim` es el **nombre del nodo** que crea; `rviz2` es otro nodo. Más adelante, al ejecutar `ros2 run robot_teleop keyboard_control`, se inicia el programa de teleoperación creado por el estudiante. El vehículo llamado `robot` en el XML es el **robot simulado**, no un nodo ROS 2.

### Topic y mensaje: el canal y lo que circula por él

Un **topic** es un canal con nombre. Un nodo **publica** mensajes en él y otros nodos se **suscriben** para recibirlos; el publicador no espera una respuesta. Un **mensaje** es la estructura tipada que se envía. No son sinónimos: `/cmd_vel` es el topic; `geometry_msgs/msg/Twist` es el tipo de mensaje, con campos como `linear.x` y `angular.z`.

| Topic | Tipo de mensaje | Sentido en la práctica |
| --- | --- | --- |
| `/scanner1` | `sensor_msgs/msg/LaserScan` | `/mvsim` publica distancias; `/rviz2` puede mostrarlas. |
| `/odom` | `nav_msgs/msg/Odometry` | `/mvsim` publica odometría. |
| `/cmd_vel` | `geometry_msgs/msg/Twist` | El teleoperador o la terminal publica velocidades; `/mvsim` las recibe. |
| `/imu` | `sensor_msgs/msg/Imu` | `/mvsim` publica lecturas inerciales. |

Un topic puede aparecer aunque solo haya publicador o solo suscriptor. Publicar una velocidad en `/cmd_vel` es **usar un topic**, no llamar a un servicio: MVSim recibe la orden, pero ese envío no produce una respuesta de petición–respuesta. La terminal que ejecuta `ros2 topic pub` actúa como publicador; no necesitas escribir un nodo propio para hacer esa prueba.

### Servicio: petición y respuesta puntual

Un **servicio** conecta a un cliente que envía una petición con un servidor que devuelve una respuesta. Es adecuado para una operación breve de la que necesitas saber el resultado: por ejemplo, «dame este dato de configuración» y recibir su valor. A diferencia de un topic, hay respuesta asociada a la petición; a diferencia de una acción, no se usa para seguir el progreso de una tarea larga ni para cancelarla.

**En la práctica 2.1 no se crea ni se llama explícitamente a un servicio de control del robot.** Aun así, al ejecutar `ros2 service list` con la simulación arrancada pueden aparecer servicios de infraestructura: si aparece `/mvsim/get_parameters`, ese sí es un servicio real. Un cliente pide el valor de uno o varios parámetros y el nodo `/mvsim` le responde; `ros2 param get /mvsim world_file` permite hacer esa consulta sin construir manualmente la petición del servicio. Comprueba qué servicios existen realmente en tu ejecución antes de usar sus nombres. No hay que inventar un servicio `/cmd_vel`: `/cmd_vel` es un topic.

### Parámetro ROS 2: configuración de un nodo

Un **parámetro** pertenece a un nodo y guarda un valor con el que este trabaja; no es un canal por el que se envían lecturas continuamente. En el fragmento de launch del notebook, el argumento `world_file` se pasa como **parámetro ROS 2** al nodo `/mvsim`: así sabe qué mundo cargar. Con el nodo en marcha se pueden consultar sus parámetros con `ros2 param list /mvsim` y, si figura `world_file`, leer su valor con `ros2 param get /mvsim world_file`. Poder cambiar un parámetro durante la ejecución depende del nodo y del parámetro: no hay que asumir que cambiar `world_file` recargue el mundo.

Hay tres niveles distintos en los materiales, aunque todos sirvan para configurar algo:

| Dónde aparece | Ejemplo | Qué configura |
| --- | --- | --- |
| Comando/archivo **launch** | `use_rviz:=false` | Si se arranca RViz2; es un argumento del launch, no un parámetro de `/mvsim`. |
| Nodo **ROS 2** | `world_file` de `/mvsim` | Qué archivo de mundo recibe el nodo al arrancar. |
| Archivo **XML** de MVSim | `sensor_period_sec="0.10"` | Cada cuánto simula una medida ese sensor; no se consulta con `ros2 param get`. |

### Acción ROS 2: objetivo, progreso, resultado y cancelación

Una **acción** sirve para una operación que puede tardar. El cliente envía un **objetivo**; el servidor puede enviar **feedback** mientras trabaja, devuelve un **resultado** al terminar y permite pedir la **cancelación**. Un ejemplo fuera de esta práctica sería encargar a un sistema de navegación «ve a esta posición» y recibir actualizaciones hasta llegar o cancelar. Publicar velocidades individuales en `/cmd_vel` **no** es una acción ROS 2 y en la práctica 2.1 no se ejecuta un servidor de acciones de navegación.

No confundas una acción ROS 2 con `ld.add_action(...)` o `Node(...)` en un archivo launch: allí «acción» significa una instrucción para lanzar procesos, no el mecanismo de objetivo, feedback y resultado de ROS 2.

**Regla rápida:** datos u órdenes que fluyen sin respuesta -> **topic**; petición breve con respuesta -> **servicio**; tarea larga con progreso/cancelación -> **acción**; ajuste de un nodo -> **parámetro**; componente que realiza el trabajo -> **nodo**. Para reconocerlos con la simulación abierta:

```bash
ros2 node list
ros2 node info /mvsim
ros2 topic info /scanner1 --verbose
ros2 service list
ros2 param list /mvsim
ros2 action list
```

La lista de acciones puede estar vacía: eso no indica un fallo, sino que no se ha lanzado ningún servidor de acciones.

### QoS de los topics

Quality of Service define políticas de entrega. Entre las propiedades que muestra `--verbose` aparecen:

- **Reliability**: entrega fiable o basada en mejor esfuerzo.
- **Durability**: si los mensajes antiguos quedan disponibles para nuevos suscriptores.
- **History/Depth**: cuántos mensajes se conservan.
- **Deadline**: intervalo esperado entre mensajes.

Para esta práctica basta con reconocer que publicador y suscriptor necesitan políticas compatibles.

## 9. Comandos de inspección

### Listar topics

```bash
ros2 topic list
```

Solo muestra nombres. No muestra tipos ni contadores.

### Información de un topic

```bash
ros2 topic info /scanner1
```

Muestra el tipo y el número de publicadores y suscriptores.

```bash
ros2 topic info /scanner1 --verbose
```

Añade nombres de nodos, tipos de endpoint y perfiles QoS.

### Leer mensajes

```bash
ros2 topic echo /scanner1
```

Imprime continuamente los mensajes. Se detiene con `Ctrl+C`.

Para recibir solo un mensaje:

```bash
ros2 topic echo /base_pose_ground_truth --once
```

### Medir frecuencia

```bash
ros2 topic hz /scanner1
```

Calcula la frecuencia observada y estadísticas temporales.

### Visualizar el grafo

```bash
rqt_graph
```

En el grafo:

- Los nodos suelen representarse como óvalos.
- Los topics suelen representarse como rectángulos.
- Las flechas indican el sentido de la información.

Si `/cmd_vel` apunta hacia `/mvsim`, significa que MVSim está suscrito. Si `/scanner1` sale de `/mvsim`, significa que MVSim lo publica.

| Topic                     | Tipo                         | Productor                   | Consumidor habitual       | Contenido                                    |
| ------------------------- | ---------------------------- | --------------------------- | ------------------------- | -------------------------------------------- |
| `/scanner1`               | `sensor_msgs/msg/LaserScan`  | `mvsim`                     | `rviz2`                   | Distancias medidas por el LiDAR 2D           |
| `/odom`                   | `nav_msgs/msg/Odometry`      | `mvsim`                     | Localización o navegación | Estimación odométrica de pose y velocidad    |
| `/base_pose_ground_truth` | `nav_msgs/msg/Odometry`      | `mvsim`                     | Evaluación                | Pose y velocidad reales de la simulación     |
| `/cmd_vel`                | `geometry_msgs/msg/Twist`    | Controlador o teleoperación | `mvsim`                   | Velocidad lineal y angular deseadas          |
| `/imu`                    | `sensor_msgs/msg/Imu`        | `mvsim`                     | Localización              | Orientación, velocidad angular y aceleración |
| `/gps1`                   | Mensaje GNSS correspondiente | `mvsim`                     | Localización              | Posición global simulada                     |
| `/tf`                     | `tf2_msgs/msg/TFMessage`     | Varios nodos                | RViz2 y navegación        | Transformaciones dinámicas entre marcos      |
| `/tf_static`              | `tf2_msgs/msg/TFMessage`     | Varios nodos                | RViz2 y navegación        | Transformaciones estáticas                   |

Que un topic no tenga suscriptores no significa que sea irrelevante. Puede ser una salida preparada para un nodo que todavía no se ha iniciado. De igual modo, `/cmd_vel` puede aparecer con cero publicadores porque MVSim ya está esperando órdenes.

## 11. Odometría y ground truth

`/odom` y `/base_pose_ground_truth` usan el mismo tipo de mensaje, pero tienen distinto significado.

### `/odom`

Representa una estimación del movimiento. En un robot real suele obtenerse integrando encoders de ruedas y, en algunos casos, fusionando otros sensores.

Puede acumular:

- Error de escala.
- Deslizamiento.
- Ruido.
- Deriva con el tiempo.

### `/base_pose_ground_truth`

Representa la pose exacta conocida internamente por el simulador. En un robot real no suele estar disponible, porque el problema de localización consiste precisamente en estimar esa pose desconocida.

### Evaluación de localización

Para evaluar un algoritmo se compara su estimación con el ground truth. Algunas métricas posibles son:

- Error de posición.
- Error angular.
- Error cuadrático medio.
- Evolución de la deriva.

El ground truth sirve para evaluar, pero no debe utilizarse como entrada del algoritmo que se pretende evaluar.

## 12. Control del robot con Twist

MVSim recibe órdenes en `/cmd_vel` con mensajes `geometry_msgs/msg/Twist`.

Su estructura contiene dos vectores:

```text
linear:  x, y, z
angular: x, y, z
```

Para un robot terrestre de tracción diferencial interesan principalmente:

- `linear.x`: velocidad hacia delante o atrás, en m/s.
- `angular.z`: velocidad de giro, en rad/s.

Los demás componentes permanecen en cero porque el robot no se desplaza lateralmente, no vuela y no rota alrededor de los ejes longitudinal o lateral.

### Avanzar

```bash
ros2 topic pub /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.5, y: 0.0, z: 0.0}, angular: {x: 0.0, y: 0.0, z: 0.0}}"
```

### Girar sobre sí mismo

```bash
ros2 topic pub /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.0, y: 0.0, z: 0.0}, angular: {x: 0.0, y: 0.0, z: 0.5}}"
```

### Describir una curva

```bash
ros2 topic pub /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.5, y: 0.0, z: 0.0}, angular: {x: 0.0, y: 0.0, z: 0.2}}"
```

### Detener explícitamente

```bash
ros2 topic pub --once /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.0, y: 0.0, z: 0.0}, angular: {x: 0.0, y: 0.0, z: 0.0}}"
```

El signo de `linear.x` decide avance o retroceso. El signo de `angular.z` decide el sentido del giro.

## 13. Publicación continua, `--once` y watchdog

Sin opciones adicionales, `ros2 topic pub` publica repetidamente hasta recibir `Ctrl+C`.

```bash
ros2 topic pub /cmd_vel geometry_msgs/msg/Twist "..."
```

Con `--once`, publica un único mensaje y termina:

```bash
ros2 topic pub --once /cmd_vel geometry_msgs/msg/Twist "..."
```

Con `--rate`, fija una frecuencia concreta:

```bash
ros2 topic pub --rate 10 /cmd_vel geometry_msgs/msg/Twist "..."
```

### Qué hace realmente Ctrl+C

`Ctrl+C` detiene el proceso publicador, pero no envía por sí mismo una velocidad cero. A partir de ese momento MVSim deja de recibir órdenes.

### Watchdog

El watchdog comprueba si las órdenes se reciben con suficiente frecuencia. Si pasa demasiado tiempo sin una nueva orden, detiene el robot.

Sin watchdog, una pérdida de comunicación podría dejar aplicada indefinidamente la última velocidad. En un robot real eso sería peligroso.

La diferencia entre confiar en el watchdog y enviar una parada explícita es:

```text
Ctrl+C -> silencio -> expira el watchdog -> parada
Ctrl+C -> mensaje Twist con ceros -> parada inmediata
```

La práctica recomendada es enviar una orden de parada y conservar el watchdog como respaldo de seguridad.

### Publicadores que compiten

Si dos nodos publican simultáneamente en `/cmd_vel`, MVSim recibe mensajes de ambos. No existe arbitraje automático para decidir cuál manda. Las órdenes pueden alternarse y provocar movimientos impredecibles.

Para diagnosticarlo:

```bash
ros2 topic info /cmd_vel --verbose
```

Debe revisarse `Publisher count` y el nombre de cada nodo publicador.

## 14. Sistemas de coordenadas

Las órdenes `Twist` se expresan en el marco local del robot:

- Eje `x`: hacia delante.
- Eje `y`: lateral.
- Eje `z`: vertical.
- Giro `angular.z`: rotación en el plano.

Esto permite ordenar "avanza" de la misma manera aunque el robot apunte al norte, sur, este u oeste.

Si las órdenes estuvieran expresadas en coordenadas globales, el controlador tendría que conocer la orientación actual y transformar continuamente el vector deseado.

ROS 2 utiliza el sistema TF para relacionar marcos como:

```text
map -> odom -> base_link -> sensores
```

- `map`: referencia global estable.
- `odom`: referencia local continua asociada a la odometría.
- `base_link`: cuerpo principal del robot.
- Marcos de sensores: posición de cada sensor respecto al robot.

## 15. Workspace, paquete y nodo propio

### Workspace

Directorio que agrupa paquetes desarrollados por el usuario. Su estructura típica es:

```text
robotics_ws/
├── src/       # Código fuente
├── build/     # Archivos intermedios de compilación
├── install/   # Resultado instalable y scripts de entorno
└── log/       # Registros de colcon
```

Las tres últimas carpetas se generan con `colcon build`.

Creación básica:

```bash
mkdir -p ~/robotics_ws/src
cd ~/robotics_ws
colcon build
```

### Overlay y source

ROS 2 Jazzy se instala normalmente en `/opt/ros/jazzy`. Al ejecutar:

```bash
source /opt/ros/jazzy/setup.bash
```

la terminal conoce los paquetes del sistema.

Después de compilar el workspace se ejecuta:

```bash
source ~/robotics_ws/install/setup.bash
```

Esto añade los paquetes propios por encima de la instalación base. Cada terminal tiene su propio entorno; hacer `source` en una no afecta a las demás.

Puede automatizarse en `~/.bashrc`, cuidando que primero se cargue ROS 2 y después el workspace.

### Paquete

Unidad de organización y distribución. Un paquete Python contiene normalmente:

```text
robot_teleop/
├── package.xml
├── setup.py
├── setup.cfg
├── resource/
├── robot_teleop/
│   ├── __init__.py
│   └── keyboard_control.py
└── test/
```

Creación:

```bash
cd ~/robotics_ws/src
ros2 pkg create --build-type ament_python \
  --dependencies rclpy geometry_msgs \
  --node-name keyboard_control \
  robot_teleop
```

- `package.xml` declara metadatos y dependencias.
- `setup.py` declara cómo instalar el paquete y sus ejecutables.
- `entry_points` relaciona un nombre ejecutable con una función Python.

### Nodo

Programa que participa en el grafo ROS 2. El nodo de teleoperación publicará mensajes `Twist` en `/cmd_vel`.

## 16. Teleoperación por teclado

El nodo debe traducir pulsaciones a órdenes:

| Tecla   | Acción               |
| ------- | -------------------- |
| `w`     | Avanzar              |
| `s`     | Retroceder           |
| `a`     | Girar a la izquierda |
| `d`     | Girar a la derecha   |
| Espacio | Detener              |

### Publicador con rclpy

El patrón fundamental es:

```python
self.publisher = self.create_publisher(Twist, '/cmd_vel', 10)
```

Para cada orden se crea un mensaje:

```python
message = Twist()
message.linear.x = 0.5
message.angular.z = 0.0
self.publisher.publish(message)
```

### Lectura inmediata del teclado

La entrada habitual de Python espera `Enter`. Para teleoperación interesa leer una sola tecla inmediatamente.

Los módulos implicados son:

- `termios`: lee y restaura la configuración del terminal.
- `tty`: activa el modo raw.
- `select`: espera entrada con timeout sin bloquear indefinidamente.
- `sys.stdin`: proporciona el flujo de entrada.

Es imprescindible restaurar el terminal en un bloque `finally`; de lo contrario, puede quedar sin eco o con comportamiento extraño después de cerrar el nodo.

### spin y bucle de teclado

`rclpy.spin(node)` bloquea el hilo mientras procesa callbacks. Si el mismo hilo debe revisar el teclado, puede utilizarse:

```python
rclpy.spin_once(node, timeout_sec=0.0)
```

Así se atienden eventos ROS 2 sin impedir que continúe el bucle de lectura.

### Cierre seguro

Al terminar conviene:

1. Publicar una velocidad cero.
2. Restaurar el terminal.
3. Destruir el nodo.
4. Ejecutar `rclpy.shutdown()`.

Esto evita dejar el robot moviéndose o el terminal en modo raw.

## 18. Diagnóstico y errores frecuentes

### Un archivo launch no se encuentra

Comprobar la ortografía completa. Por ejemplo, `launch.py` y no `lauch.py`.

```bash
ros2 launch mvsim demo_indoor_outdoor.launch.py
```

### Aparecen topics de sensores desactivados

RViz2 puede crear suscripciones para displays configurados aunque MVSim no publique esos sensores. El nombre puede aparecer en el grafo con:

```text
Publisher count: 0
Subscription count: 1
```

La comprobación correcta es:

```bash
ros2 topic info /cam1/image_raw --verbose
```

### El robot se mueve sin querer

Buscar publicadores activos de `/cmd_vel`:

```bash
ros2 topic info /cmd_vel --verbose
```

También puede inspeccionarse el contenido:

```bash
ros2 topic echo /cmd_vel
```

Un `ros2 topic pub` anterior puede seguir ejecutándose en otra terminal.

### Distinguir movimiento real de movimiento de cámara

Leer dos veces el ground truth y comparar `position.x` e `position.y`:

```bash
ros2 topic echo /base_pose_ground_truth --once
```

Si la pose no cambia, el robot está quieto y solo se ha movido la vista.

### Un paquete propio no aparece

Comprobar:

1. Se ha compilado desde la raíz del workspace.
2. La compilación no produjo errores.
3. Se ha ejecutado `source install/setup.bash` en esa terminal.
4. El paquete está dentro de `src/`.

```bash
ros2 pkg list | grep robot_teleop
```

### Un ejecutable no aparece

Revisar `entry_points` en `setup.py`, recompilar y volver a cargar el entorno:

```bash
colcon build --packages-select robot_teleop
source install/setup.bash
ros2 pkg executables robot_teleop
```

### El XML deja de cargar

Los fallos comunes son:

- Etiqueta sin cerrar.
- Comillas ausentes.
- `<include>` fuera de `<vehicle>`.
- Ruta relativa incorrecta.
- Atributo mal escrito.

Conviene realizar cambios pequeños y guardar una copia del bloque original.

## Ideas esenciales para recordar

- MVSim simula la realidad; RViz2 visualiza mensajes ROS 2.
- Los nodos son independientes y se conectan mediante interfaces tipadas.
- Un topic puede existir con un solo extremo de comunicación.
- La odometría es una estimación; el ground truth es una referencia de evaluación.
- `/cmd_vel` expresa la velocidad deseada en el marco local del robot.
- Una parada explícita es control normal; el watchdog es protección ante fallos.
- Un workspace propio debe compilarse y cargarse en cada terminal.
- La arquitectura modular permite sustituir simulación, visualización o control sin rediseñar todo el sistema.
